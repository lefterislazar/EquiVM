# Solidity storage algorithms across the via-IR compilers (solc 0.8.0–0.8.37)

**Question.** `solidityStorageBackend` (`Solm/SolidityStorage.lean`) takes the layout as a parameter
(`StorageLayout`, generated by `solidityLayout!`) and fixes the storage algorithms. Solidity has no
modular-language requirement, so the algorithms only need to be a parameter if solc versions
implement storage differently. Do they?

**Answer.** Mostly no. On storage that Solidity code itself could have written, every release from
0.8.1 to 0.8.37 implements every storage operation probed here with the same behaviour, apart from
two compiler bug fixes:

- **0.8.32:** clearing of arrays that straddle slot 2²⁵⁶.
- **0.8.34:** transient/persistent `delete` collision, affecting 0.8.28–0.8.33.

One further change, in **0.8.16**, only shows on non-canonical storage: bytes past a packed array's
last element are now zeroed. The storage layout is identical across all versions.
**Recommendation: keep the algorithms fixed and the layout parametric (option B).** On
non-canonical storage the behaviour also depends on the pipeline (see "The legacy pipeline"), so
either assume canonical storage with a `StorageWF` precondition or fix one pipeline per semantics.

Generated tables are in [`MATRIX.md`](MATRIX.md) and machine-readable results in
[`summary.json`](summary.json).

## Method

1. **Probes** (`probes/*.sol`, 10 contracts, 210 operations) cover:
   - every storage type family: packed and full-word value types, enum, contract and function
     types; structs (nested, with a mapping); fixed and dynamic arrays (packed, multi-slot, nested,
     of `bytes`); `bytes`/`string`; mappings with value and dynamic keys; transient value types;
     `layout at`; arrays placed at arbitrary slots with inline assembly
   - every operation of `StorageBackend`: read, write from memory/calldata/storage, `delete`,
     length, `push()`, `push(v)`, `pop()`, index read/write/delete
2. **Static** (`run_matrix.py`, `yul_extract.py`, `analyze.py`):
   - Every probe is compiled with all 38 releases from 0.8.0 to 0.8.37 (`settings.viaIR`,
     optimizer off), taking the unoptimized IR.
   - Each operation's Yul helper closure is extracted and normalized: comments and AST ids are
     dropped, locals renamed by position, literals printed in decimal.
   - Closures are hashed *structurally*, by Merkle-hashing each helper's body with callee names
     replaced by the callees' hashes, so helper renames do not count as changes.
   - At every boundary, only the helpers whose own code changed are reported, with their diffs in
     `out/diffs/`.
3. **Dynamic** (`scenarios.py`, `dynamic.py`):
   - 108 call-sequence scenarios run against every version's via-IR runtime code in anvil
     (`debug_traceCall` with state overrides; a forwarder runs a scenario's calls in one
     transaction, so transient storage persists across them).
   - Versions are grouped by what is observable: each call's success and return or revert data,
     plus the final storage.
   - Scenarios include non-canonical states (dirty bytes past a value's length, invalid
     `bytes` headers, out-of-range enum values) and arrays straddling 2²⁵⁶.
4. **Conformance:** each helper family is compared with its Lean counterpart on `origin/solidity`.

### Checks on the method

- **Known bugs rediscovered.** The analysis finds both via-IR storage bugs in solc's `bugs.json`
  at their exact fix versions, statically *and* dynamically:
  - `LostStorageArrayWriteOnSlotOverflow` (fixed 0.8.32)
  - `TransientStorageClearingHelperCollision` (0.8.28–0.8.33)

  `DirtyBytesArrayToStorage` (fixed 0.8.15) correctly does *not* show up: per `bugs.json` it only
  affects the legacy pipeline.
- **Dynamic ⊆ static.** Every version where some scenario's behaviour changes is also a static
  boundary. No behavioural change escaped the static analysis.
- **Deterministic.** A full rebuild gives the same 7,372 closure hashes.
- **Coverage gaps:**
  - 0.8.0 emits no via-IR bytecode, so it is analysed statically only.
  - A few 0.8.0/0.8.1 operations hit `UnimplementedFeatureError`/ICE: calldata `bytes`/`string`
    mapping keys; `delete` of a struct containing a mapping; reading a struct with dynamic members
    into memory; `push` of a memory array, struct or `bytes`; deleting external function types.
  - Releases are taken from binaries.soliditylang.org (sha256 recorded in
    `out/raw/manifest.json`).

## Findings

### Storage layout: invariant

The `--storage-layout` output (slot, offset, encoding and size of every variable) is identical for
every probe in every version where the probe compiles. Only features appear:

- transient storage in 0.8.28, with value types only
- `layout at <base>` in 0.8.29

The compiler rejects a `layout at` whose static variables would wrap past 2²⁵⁶, so a straddling
array needs an assembly `.slot` assignment.

### Algorithm boundaries

Twelve versions change some operation's normalized helper closure. Reading the diffs and checking
them against the dynamic results sorts them into four groups.

**Behaviour-preserving (8): no observable effect.**

| version | change |
|---|---|
| 0.8.1 | best effort, not verifiable (0.8.0 has no bytecode); completes the experimental codegen |
| 0.8.2 | `storage_set_to_zero` restructured; storage-pointer conversions in push/pop |
| 0.8.4 | long-bytes index access factored out |
| 0.8.5 | tail clearing factored into `cleanup_storage_array_end` / `clean_up_bytearray_end_slots` |
| 0.8.8 | `identity()` wrapper in conversions |
| 0.8.15 | storage→memory copy of empty bytes no longer over-allocates (memory only) |
| 0.8.17 | `checked_mul` restructured |
| 0.8.25 | `mcopy` (memory only) |

**Representation change (1).**

| version | change | observed |
|---|---|---|
| 0.8.7 | internal function pointers stored as sequential ids instead of AST ids | `ValueTypes.fi` |

Solm does not model `function` values (`wordToElem .function` is a TODO), so this is out of scope.

**Semantic, but only on non-canonical storage (1).**

| version | change | observed |
|---|---|---|
| 0.8.16 | packed arrays copied into storage a whole slot at a time; bytes past the last element are zeroed instead of kept | `FixedArrays.p.dirty.write`, `DynArrays.p.dirty.grow` |

Witness: `uint8[5] p` over a slot of `0xff…`. Up to 0.8.15, writing `[1,2,3,4,5]` leaves
`0xff…ff0504030201`; from 0.8.16 it leaves `0x0504030201`.

**Semantic: bug fixes (2).**

| version | change | observed |
|---|---|---|
| 0.8.32 | clearing loops count instead of comparing absolute slots | `SlotPointers.box.wrap`, `SlotPointers.pbox.wrap` |
| 0.8.34 | transient clearing gets its own helper | `TransientCollision.delete-persistent` |

The witnesses:

- **0.8.32.** In ≤0.8.31,
  `clear_storage_range(start, end)` is `for {} lt(start, end) {start := add(start, 1)}`, so a range
  that wraps past 2²⁵⁶ is empty. Deleting a `uint256[4]` placed at 2²⁵⁶−2 clears nothing. From
  0.8.32 the loop counts `i < slotCount` and clears all four slots. The same rewrite touches
  `clean_up_bytearray_end_slots`, `cleanup_storage_array_end` and `clear_storage_array`
  (73 operations statically). Only straddling arrays behave differently.
- **0.8.34.** In 0.8.28–0.8.33, a contract that deletes both a persistent and a transient
  `uint256` gets one `storage_set_to_zero_t_uint256` helper, which calls
  `update_transient_storage_value`. After `w_both(7); delete p;` the persistent `p` is still 7 and
  the transient `t` is 0. From 0.8.34 there is a separate `transient_storage_set_to_zero_*`.

## Conformance of the EquiVM backend

Each Yul helper family was compared with its Lean counterpart on `origin/solidity`, using the
observed behaviour from the dynamic runs. **This is by inspection; the Lean semantics was not
executed on these scenarios.**

**Canonical storage: Lean agrees with 0.8.34+.** It also agrees with every older class from 0.8.1
on, except for the two bug-fixed behaviours: transient collisions in 0.8.28–0.8.33, and straddling
arrays up to 0.8.31.

| Yul | Lean | agreement |
|---|---|---|
| `extract_byte_array_length`, panic 0x22 | `solidityDecodeBytesLengthHeader` → `.revert` | same predicate; every op on an invalid header reverts, including index access (bounds checks go through `backend.length`) |
| `copy_byte_array_to_storage_*`, `clean_up_bytearray_end_slots` | `solidityWriteBytesValue?` | same words cleared (`ceil(new/32)..ceil(old/32)`, all when the new value is short); last data word zero-padded |
| `byte_array_pop`, `transit_byte_array_long_to_short` | pop via read and rewrite | same final state |
| `resize_array` + copy, `cleanup_storage_array_end` | `.dynamicArray` arm: clear all, write, set length | same final state |
| `array_push_zero_*` (length only; the new element is *not* zeroed) | `solidityPushStorage? … none` (length only) | identical even on dirty storage |
| `array_pop_*` | clears the element, then the length | identical |
| `storage_set_to_zero`, `clear_storage_range` | `solidityClearStorage?`, mappings skipped | same on canonical storage |
| `update_storage_value_offset_*`, `extract_from_storage_value_*` | `storageLocStore` / `storageLocLoad` | identical, including bool (`0x02` reads as `true`) |
| straddling arrays | layout slot arithmetic is `UInt256` addition and wraps | matches ≥0.8.32 |
| transient `delete` | separate transient backend | matches ≥0.8.34 |

**Non-canonical storage: six divergences.** All need storage that compiled Solidity code does not
produce (assembly, a delegatecall into another layout, or another compiler). Items 1, 3 and 4 were
missed in the first version of this report and found while implementing the via-IR algorithms,
by reading the closures in `out/closures/0.8.37.json`:

1. **`delete` of a struct.** via-IR's `clear_struct_storage` writes `sstore(slot, 0)` for every
   slot holding value-type members; Lean clears each member in place, keeping the slot's padding.
2. **`delete` of a packed array**, and clearing the tail of a dynamic array. solc zeroes whole
   slots; Lean zeroes each element and keeps a dirty tail.
3. **Assigning a packed array over a dirty slot tail.** Lean clears and writes per element, so the
   tail survives. This matches ≤0.8.15 but not 0.8.16+, which writes whole slots.
4. **`push(v)` and `pop()` on dirty `bytes`.** solc changes the header and the one byte in place
   (`array_push_from_t_bytes1`, `byte_array_pop`); Lean rewrites the whole value, which zeroes the
   bytes past the new length.
5. **`push()` on dirty `bytes`.** Lean rewrites the value with a zero byte. solc only increases the
   length, exposing the dirty byte (`Bytes.b.dirty.short`, `Bytes.b.dirty.long`).
6. **Enum value out of range.** solc reads panic 0x21. Solm has no enums, and a `uint8`
   desugaring returns the raw value.

The refinement relation already has the hook to make these irrelevant:
`runtimeRefinementWithWF (wf : StorageWF)` (`Solm/Refine.lean`). Note that DiffTest's random
pre-states (`Solm/DiffTest/Gen.lean`, `randomStorage`) are written *through* the backend, so they
are canonical and cannot expose these cases.

## The legacy pipeline

The analysis above covers via-IR only. Most benchmarks EquiVM has proved are compiled with the
legacy code generator (WETH9 with 0.5.16, Dss with 0.6.12, Auction with 0.8.23), so
`legacy_compare.py` runs every scenario on legacy bytecode of 0.8.4, 0.8.13, 0.8.23 and 0.8.37
and compares it with the via-IR bytecode of the same release:

| scenario | legacy vs via-IR |
|---|---|
| `Structs.S.dirty` | **differs in every release**: legacy `delete` of a struct masks out each member and keeps the padding; via-IR zeroes whole slots |
| `SlotPointers.box.wrap`, `pbox.wrap` | differ up to 0.8.31; both pipelines fixed in 0.8.32 |
| `ValueTypes.fi` | internal function pointer encoding (not modelled) |
| all other 103 scenarios | identical, including the packed-array writes, packed-array `delete` and `bytes` push/pop on dirty storage |

Releases before 0.8 were not run (the probes use 0.8 syntax). The Flipper proof
(`Benchmarks/Dss/Flipper/BidDelete.lean`) shows the per-member struct `delete` of 0.6.12.

So on non-canonical storage the struct `delete` of the current Lean backend matches legacy
bytecode and not via-IR. Changing `Solm.solidityStorageBackend` to via-IR behaviour would make the
proved legacy benchmarks false on dirty storage.

## Recommendation

**Option B: fixed algorithms, parametric layout.** The parameter surface the data supports:

- **Layout:** the base slot (`layout at`, 0.8.29+) and the location (persistent or transient), as
  `solidityStorage!` / `solidityTransientStorage!` already do. Nothing else in the layout varies
  across 0.8.x.
- **Algorithms:** none on canonical storage. The current Lean algorithms implement the bug-fixed
  semantics (≥0.8.34) there.
- **Version scope:** state it as **solc ≥ 0.8.34**. Older versions are also covered, with two
  exceptions:
  - 0.8.28–0.8.33, for contracts that `delete` both a transient and a persistent variable of the
    same type
  - ≤0.8.31, for arrays straddling 2²⁵⁶
- **Non-canonical storage:** the behaviours depend on the pipeline (struct `delete`) and on the
  release (packed-array writes before 0.8.16), so a single algorithm cannot match every compiler.
  Either assume canonical storage (`StorageWF`), or fix one pipeline per semantics.

### Outcome

- `Solm.solidityStorageBackend` is unchanged, so the legacy benchmarks keep their behaviour.
- The Solidity semantics (`Solidity/`, branch `solidity-storage-implementation`) no longer goes through
  a configurable `StorageBackend`. Its config carries only the layout (`Config.storageLayout`); the
  algorithms are fixed in `Solidity/Storage.lean` and follow via-IR ≥0.8.34 on all storage,
  removing divergences 1–5 there. A differential scenario (`Solidity/Test/Scenarios/ViaIRStorage.lean`)
  checks them against `solc 0.8.35 --via-ir` bytecode on seeded dirty storage.

## Reproducing

```
solc-select install 0.8.0 … 0.8.37        # binaries in ~/.solc-select/artifacts
python3 run_matrix.py --jobs 12             # out/raw/<version>/<probe>.json (≈10 s)
python3 yul_extract.py                      # out/closures/<version>.json
python3 analyze.py                          # out/analysis.json, out/diffs/, out/layouts.json
python3 dynamic.py                          # out/dynamic.json (needs anvil and cast; ≈1 min)
python3 report.py                           # summary.json, MATRIX.md
python3 legacy_compare.py                   # legacy vs via-IR on every scenario (≈2 min)
```

Adding a probe operation means adding a function named `<op>_<target>`
(`w|r|d|wf|rf|wi|ri|di|len|push0|pushv|pop|rmw`) to a probe contract. Other functions (such as
the `set_*2` setters) are shared declarations and are not analysed.
